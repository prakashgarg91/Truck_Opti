### Ranked gaps that block selling the product

Ranked by direct impact on whether a paying customer can complete the journeys the product sells. Owner-gated proof items are ranked last (they gate "production-ready" claims, not code, and cannot be advanced without owner credentials).

1. **The core marketplace loop has no working production path — a booking can never reach a driver.** (a) Nothing in the repo INSERTs into `job_offers`: agency dispatch only sets `agency_jobs.driver_id` (supabase/functions/agency-portal-jobs/index.ts:125-153; offers row "Agency assigns a driver"), the sole insert being a service-role fixture (scripts/live-auth-proof.cjs:206-216). (b) Customer booking toasts "Notified N drivers" via RPC `dispatch_job_to_drivers`, which exists in no migration or edge function (frontend/src/pages/NewShipmentPage.tsx:93; customer row "Driver dispatch after booking"). (c) Driver Accept/Decline still uses two direct browser UPDATEs on `job_offers`/`drivers` whose driver UPDATE policy was dropped by the OTP-hardening migration (20260730110000:96) with no replacement RPC (offers rows "Accept"/"Decline"/"hardening") — acceptance is RLS-denied today. Until TO-129's accept RPC and a real dispatch producer exist, the product's central promise is inert.
2. **Driver self-approval: privileged verification status is client-writable via RLS.** "Drivers: own record" is `FOR ALL` with no column restriction (20260418003000:128-137) — a driver client can set its own `status='approved'`, `total_trips`, `rating`; the online/approval gate is React-only (offers row "online/offline toggle"; kyc row "drivers.status integrity"). This defeats the driver-vetting story a logistics marketplace sells and must be closed with a DB-level status write lock before any onboarding of real drivers.
3. **KYC is a client simulation and driver identity documents are publicly readable.** No KYC backend exists at all — no tables, no edge function, no server-computed verified state (kyc rows "durable authoritative KYC backend", "Submit for verification", "KYC Verified banner", "?demo=midflow"); the only real upload writes licence/RC to the public `driver-docs` bucket and stores permanent public URLs (DriverRegisterPage.tsx:80-91; "Public can view driver documents", 20260306000000:26-29). trip-photos and billing-documents buckets are also public, and billing-documents admin policy trusts forgeable `user_metadata.role` (20260517010000:26-37) — a live privilege-escalation + PII exposure (Aadhaar-class documents, invoice PDFs). TO-126/127/128 are unimplemented; this is a legal/compliance blocker, not a polish item.
4. **Revenue lifecycle is incomplete and unproven; subscription economics cannot operate.** No executed valid/invalid order creation, webhook-replay, or forged-callback proof exists — TO-137 is owner-blocked (payments rows "Order creation", "HMAC verification", "idempotent webhooks", "negative paths"). Independently of gating: `payment.failed` never reconciles server-side (razorpay-webhook/index.ts:202 handles only `payment.captured`), a subscriber cannot cancel (subscriptionApi.ts:211-213 throws; no server writer), there is no renewal machinery at all, usage meters never increment (no callers of `usageApi.increment`), and the free tier provisions nothing. Recurring revenue currently depends on users manually re-initiating checkout and silently lapsing otherwise.
